## Architecture deliverables
1. Implement complete `PuzzleEngine.legal_actions(definition, state, piece_id?)` enumeration for each active piece in deterministic stable piece-ID + direction + distance + gate-ID order. Include EVERY reachable intermediate grid landing, not merely maximum slides. A rigid connected polyomino translates only; check the ENTIRE footprint at EACH intermediate step. Walls, other active pieces, board boundary and disabled blockers are respected. No pushing, overlap, rotation, diagonal movement, teleportation or no-op actions.
2. Use existing `PuzzleAction.move(piece_id, direction, landing)` for any reachable landing. Use existing `PuzzleAction.exit_through(piece_id, gate_id)` for exits. **Resolve exit direction unambiguously from a uniquely sided gate**, and ensure the chosen piece can reach a legal boundary alignment in a straight cardinal slide; a piece must never exit by teleporting, jumping collisions or exiting through an incorrect direction. Document/agree whether EXIT may include the continuous final slide-to-gate in one drag and charge exactly one move; make solver, rules and witness replay consistent.
3. Gate aperture requires the crossing footprint of the ENTIRE translated piece (orthogonal silhouette projection) to fit inclusively in `lo..hi`. Validate side/width, accepted logical color, OPEN state, exit alignment and unambiguous gate selection. Distinct-color overlapping spans allowed by TD-1 schema MUST remain deterministic. Never invent full-side fallback. Do not confuse shape width with exit projection width.
4. Extend `PuzzleEngine.transition(state, action, definition)` for supported TD-2 **simple open-gate scenarios only**: validate definition/state/action rigorously, refuse forged/unreachable landings and exits, deep-copy state, atomically commit one MOVE/EXIT and increment `move_number` once, emit deterministically ordered typed events, preserve input state unchanged; rejected actions produce `ok:false, next_state:null, events:[], error`. No-op/reverse ambiguity and malformed target/direction must reject.
5. Preserve fail-closed handling of **all** advanced mechanics from TD-1 (triggers, locked gates, counter gates, blockers, hidden pieces, rotation, timers, dynamically changing goals) with explicit `UNSUPPORTED_FEATURE`, until their respective milestones; never silently ignore an advanced feature, and never falsely return a solver solution. Use `PuzzleState` canonical data/hashes. Consider `move_number` in canonical state, but avoid making BFS treat identical board+mechanic states at different move counts as distinct search nodes. **Document and implement a search-equivalence key that excludes cumulative move count while including all mutable gameplay-relevant mechanic flags.** Keep canonical snapshot hashes unchanged if possible.
6. Implement `SolverV2.solve(definition, initial_state, max_states, ...)` (or an equivalent documented API) via BFS for shortest number of committed moves on small/medium puzzles. It MUST call `PuzzleEngine.legal_actions` and `PuzzleEngine.transition`; reconstruct `PuzzleAction` witness path and verify it by replay. Result statuses: `SOLVED`, `UNSOLVABLE` only after exhaustive search, `UNKNOWN_CAP_REACHED` if budget reached, and `INVALID_LEVEL` with schema diagnostics. Do not invent an unreachable/solvable answer. Use consistent state-cap boundary semantics and deterministic queue/action ordering. Include explored states, solution length, and reproducible witness.
7. Explicitly define win: all `required` pieces inactive (all legacy pieces are required); optional pieces need not exit. Do not infer win merely from empty/shortened arrays if active flags remain. Validate start-state integrity and avoid treating an invalid or unsupported puzzle as solved.
8. Keep output suitable for later TD-3 integrated play and TD-4 event/state extensions, without implementing those later milestones now.

## Required adversarial and reference tests
